1~2个月): 核心： 1个教材单元 + AI口语对话 + 智能跟读。 技术： Go + Gin + PostgreSQL + Dify/Coze (低代码编排)。 目的： 验证“VAD自动触发”和“流式TTS”的体验。如果对话卡顿超过1.5秒，项目直接失败，先解决延迟再谈功能。   Phase 2 (能力闭环 - 3~4个月): 核心： 加入阅读、写作、手写。 技术： 自研AI编排层（替换Dify），接入向量数据库，实现RAG教材同步。 目的： 跑通“学-练-测”闭环，验证用户留存。   Phase 3 (规模化 - 6个月+): 核心： 个性化路径、多角色、社区。 技术： 模型微调（Fine-tuning），降低Token成本；K8s部署。    3. 给Go开发者的特别提示 不要手写WebSocket状态机： 使用 gorilla/websocket 或 nhooyr.io/websocket，配合 context.Context 做超时控制。 AI调用异步化： 永远不要在HTTP Handler里同步等待LLM。使用 Channel 或 ErrGroup 处理流式响应，前端用 SSE (Server-Sent Events) 接收文本，用 WebSocket 接收音频。 SQLite的替代： 如果实在不想运维PostgreSQL，初期可用 Turso (LibSQL)，它是SQLite的分布式版本，支持HTTP/WebSocket访问，适合Serverless/边缘计算，但生产环境仍推荐PG。    📝 总结：你的系统核心竞争力 不是“AI聊天”，而是“AI私教”。  传统APP： 用户点按钮 -> 说话 -> 点停止 -> 等3秒 -> AI回复。 你的系统： 用户开口 -> AI自动听 -> 用户停顿 -> AI 0.8秒内接话 -> 用户插嘴 -> AI自动闭嘴 -> 对话结束 -> AI主动复盘。  下一步行动建议： 1. 放弃SQLite，立刻搭建 PostgreSQL + Redis 环境。 2. 先做“语音链路Demo”：用Go写一个WebSocket服务，对接Azure/阿里云的流式STT/TTS，测试在弱网下的表现。 3. 定义“教材数据结构”：不要存PDF，要存JSON/Markdown，把课文拆解为 Scene（场景）、KeyVocab（核心词）、GrammarPoint（语法点）。
